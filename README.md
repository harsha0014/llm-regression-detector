# LLM Regression Detection System

## One‑Paragraph Summary

This repository contains a production‑ready CI/CD pipeline that automatically detects quality regressions in LLM‑powered features. Every time a prompt or model changes via a GitHub Pull Request, the system runs a suite of human‑labeled test cases against the new version, compares the results to the previous run (stored in a SQLite database), and blocks the merge if semantic accuracy drops below a configurable threshold. It generates an HTML diff report, posts a detailed comment on the PR, and sends a Slack alert to the team. The entire pipeline runs inside a Docker container via GitHub Actions.

## Key Features

- Automated Regression Detection – Runs on every PR that modifies prompts or the golden dataset.
- Multi‑Dimensional Scoring – Checks category match, summary relevance (DeepEval LLM‑as‑judge), latency, and token usage.
- Diff Logic – Compares every new run against the previous run; identifies regressions (pass→fail) and improvements (fail→pass).
- Statistical Thresholds – Configurable warning (3%) and critical (8%) deltas. Critical regressions block the merge.
- Drift Detection – Tracks rolling average over the last 7 runs; alerts on slow, gradual degradation.
- Visual Reporting – Generates a standalone HTML report with scorecards, trend charts, and side‑by‑side regression tables.
- Slack Alerts – Sends structured notifications with headline metrics and a link to the full report.
- Containerized – Runs identically locally and in the cloud via Docker.
- CI/CD Native – Fully integrated with GitHub Actions; caches the evaluation database to compute deltas across commits.

## Architecture & How It Works

1. Versioned Prompts – Every prompt is stored as a YAML file with a version ID, timestamp, system prompt, and few‑shot examples.
2. Golden Dataset – A JSON file containing hand‑labeled test cases (input, expected category, expected summary, difficulty, notes). Never generated by an LLM – ground truth is human‑verified.
3. Test Runner – On each PR, the run_evaluation() function loads the prompt and dataset, runs every test case asynchronously through the LLM feature, and collects raw outputs.
4. Scoring – Each result is scored on category match, summary relevance (via DeepEval GEval), latency, and token usage.
5. Diffing – The system retrieves the previous run from SQLite, computes pass‑rate deltas, per‑category deltas, and lists of regressions/improvements.
6. Thresholds – If the pass‑rate drop exceeds 3% → warning; exceeds 8% → critical (merge is blocked).
7. Reporting – An HTML report is generated with scorecards, trend charts, and regression tables.
8. Alerting – Slack receives a structured notification; the PR gets a detailed comment; the HTML report is uploaded as an artifact.

## Setup & Running Locally

Prerequisites:
- Python 3.11+
- Docker Desktop (optional, for local container testing)
- OpenAI API key (set as environment variable)

1. Clone the repository:
git clone https://github.com/harsha0014/llm-regression-detector.git
cd llm-regression-detector

2. Set up environment variables:
Create a .env file in the root directory:
OPENAI_API_KEY=sk-proj-...
SLACK_WEBHOOK_URL=https://hooks.slack.com/services/...  # Optional

3. Run the evaluation locally (without Docker):
pip install -r requirements.txt
python run_eval.py

4. Run the evaluation inside Docker:
docker build -t regression-detector .
docker run --env-file .env -v ${PWD}:/app regression-detector

After the run, open report.html in your browser to view the dashboard.

## CI/CD Pipeline (GitHub Actions)

The workflow is defined in .github/workflows/eval.yml. It triggers on any PR that modifies files under prompts/ or golden_dataset/.

- Cache – The eval_runs folder is cached across commits on the same PR branch. This allows the system to compute deltas against previous runs.
- Docker Build – The image is built and the eval runs inside a container.
- Artifacts – eval_output.txt and report.html are uploaded for inspection.
- PR Comment – A bot posts a formatted table with metrics, delta, and regression count.
- Merge Blocking – If a critical regression is detected, the job exits with code 1, marking the PR as failed and preventing automatic merge.

## Adding New Test Cases

To expand the golden dataset, edit golden_dataset/golden_v1.json.

Each test case must include:
- id – Stable, unique identifier (e.g., tc_001)
- input – The email text
- expected_category – One of billing, technical, account, general
- expected_summary – The ideal one‑sentence summary
- difficulty – easy, medium, or hard
- notes – Why this case is important (edge case, ambiguity, etc.)

After adding new cases, commit and push. The pipeline will automatically include them in the next run.

## Adjusting Thresholds

Thresholds are defined in run_eval.py:
threshold_warning = 0.03   # 3% drop → warning
threshold_critical = 0.08  # 8% drop → critical (blocks merge)

You can also override them via environment variables in the GitHub Actions workflow.

## Architecture Decisions & Rationale

- Why SQLite over a cloud DB? – Zero infrastructure, portable, git‑friendly. Since the cache is persisted via GitHub Actions, it works perfectly for a CI pipeline.
- Why DeepEval (GEval) instead of RAGAS? – DeepEval is lighter, cheaper, and uses the same gpt-4o-mini model. It provides a deterministic LLM‑as‑judge for summary relevance.
- Why HTML over Streamlit? – Static HTML files are easy to upload as artifacts, attach to PRs, and open without hosting a server.
- Why gpt-4o-mini over gpt-4o? – The architecture is model‑agnostic; mini is 10x cheaper and sufficient for regression testing. Swapping to gpt-4o is a one‑line change.
- Why Docker? – Ensures reproducibility across local machines and GitHub runners.
